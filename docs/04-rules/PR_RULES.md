# PR Rules

> PR은 코드 변경의 기록이자 팀의 커뮤니케이션 공간입니다.  
> 작성자와 리뷰어 모두 이 규칙을 기준으로 움직입니다.

---

## 기본 원칙

- PR은 **하나의 목적**에만 집중 (기능 + 버그수정 + 리팩토링 섞지 않기)
- 머지 전 **리뷰어 1명 이상 승인** 필수
- **CI가 통과하지 않으면 머지 불가**
- 머지 후 해당 브랜치는 **즉시 삭제**
- `main`, `develop` 직접 푸시 금지 — **반드시 PR을 통해서만 머지**

---

## PR 제목 형식

브랜치 규칙의 커밋 타입과 동일한 형식을 사용합니다.

```
[타입] 작업 내용 요약
```

```
[feat] 카카오 소셜 로그인 추가
[fix] 모바일 네비게이션 메뉴 미닫힘 수정
[hotfix] 주문 API 타임아웃 임계값 조정
[refactor] 인증 서비스 레이어 분리
[style] 전체 파일 Prettier 포맷팅 적용
[chore] GitHub Actions Node 18 → 20 업그레이드
[setup] Docker Compose 초기 설정 추가
[docs] 결제 도메인 분석 초안 작성
```

---

## PR 크기 가이드

| 크기 | 변경 줄 수 | 리뷰 소요 시간 |
|---|---|---|
| 소 | ~200줄 | 30분 이내 |
| 중 | 200~500줄 | 1~2시간 |
| 대 | 500줄 이상 | 별도 협의 필요 |

500줄이 넘어가면 PR을 나눌 수 있는지 먼저 고민해 주세요.  
나누기 어렵다면 PR 올리기 전에 팀 채널에 먼저 공유하고 리뷰 일정을 잡으세요.

---

## 머지 방식 — Squash Merge

`develop` ← `feature/*` 머지 시 **Squash merge**를 사용합니다.

```
feature 브랜치 커밋 내역          develop 머지 후
──────────────────────    →    ─────────────────
feat: 초안 작성                  feat: 카카오 소셜 로그인 추가
wip: 임시 저장
fix: 오타 수정
feat: 카카오 소셜 로그인 추가
```

**이유:** 브랜치 작업 중 생기는 `wip`, `fix: 오타` 같은 과정용 커밋이 `develop` 히스토리에 남지 않아 로그가 깔끔하게 유지됩니다.

> **단, hotfix는 예외입니다.**  
> `hotfix/*` → `main` 머지 시에는 Merge commit을 사용해 흔적을 명확히 남깁니다.

## Draft PR

작업이 완료되지 않았지만 **조기 피드백이 필요하거나 방향을 공유하고 싶을 때** Draft PR을 활용하세요.

**언제 쓰나요?**
- 설계 방향이 맞는지 먼저 확인받고 싶을 때
- 작업 중인 내용을 팀에 공유해두고 싶을 때
- 큰 PR을 나누기 어려워 진행 상황을 보여줄 때

**규칙**
- Draft 상태에서는 머지 불가 — 리뷰 요청 전 **Ready for Review로 전환** 필수
- Draft PR도 제목과 설명은 동일한 형식으로 작성
- 리뷰어를 미리 지정해두면 준비됐을 때 빠르게 리뷰 요청 가능

---

## Self Review 체크리스트

PR을 올리기 전, 리뷰어에게 넘기기 전에 **본인이 먼저 확인**하세요.  
리뷰어가 발견하기 전에 본인이 잡을 수 있는 것들입니다.

### 공통

- [ ] PR 제목과 타입이 브랜치 규칙과 일치하는가?
- [ ] PR 하나에 하나의 목적만 담겨 있는가?
- [ ] 불필요한 파일(빌드 결과물, `.DS_Store`, 로컬 설정 등)이 포함되지 않았는가?
- [ ] 디버그용 로그, 주석 처리된 코드가 남아있지 않은가?
- [ ] CI가 통과했는가?

### 코드

- [ ] 변수명·함수명이 의도를 명확히 드러내는가?
- [ ] 예외 케이스가 처리되어 있는가?
- [ ] 하드코딩된 값이 없는가? (매직 넘버, 직접 박힌 URL 등)
- [ ] 민감 정보(API 키, 비밀번호 등)가 포함되지 않았는가?

### 테스트

- [ ] 변경된 기능에 대한 테스트가 작성되어 있는가?
- [ ] 기존 테스트가 전부 통과하는가?

---

## 리뷰어 에티켓

### 작성자

- PR 설명에 **무엇을, 왜 변경했는지** 명확히 작성
- 리뷰어가 맥락을 파악할 수 있도록 관련 이슈 번호 링크
- 리뷰 요청 후 **당일 또는 익일** 응답 확인

### 리뷰어

- 리뷰 요청을 받으면 **1 영업일 이내** 응답 (바로 리뷰가 어려우면 언제 가능한지 코멘트)
- 코드가 아닌 **사람을 비판하지 않기** — "이 코드는 ~" O, "당신은 ~" X
- 단순 의견은 `nit:` 접두사로 표시 — 머지를 막지 않아도 되는 사소한 제안

```
nit: 변수명을 data보다 orderList로 하면 더 명확할 것 같아요.
```

- 변경을 요청할 때는 **이유와 대안**을 함께 제시
- 좋은 코드엔 칭찬도 남기기 👍
